# 共享前缀注意力入门教学与面试问答

## 1. 一句话结论

这个项目把多个请求相同的开头组织成树，让昇腾卡尽量一起处理共享内容，并研究什么时候省下的读取值得新增的分组和合并成本。

## 2. 背景与用途

假设四个人针对同一篇文档提问。每个人的问题不同，但输入开头都是同一篇文档。模型生成答案时，会不断查看此前内容，决定哪些信息对当前输出重要，这个过程叫注意力。

如果每个请求都各自保存、读取一整份文档对应的中间数据，就会有重复。共享前缀的思路是把相同开头放到一起使用，私人问题部分仍各自保留。

不过，数据共享不代表答案共享。四个人问的问题不同，对同一段文档的关注也不同。项目必须在复用读取的同时，为每个请求算出自己的完整注意力结果。

## 3. 核心概念

### 查询与已存内容

**大白话：** 可以把当前查询理解成“这一步想找什么”，把过去内容保存的中间数据理解成“可以查阅的索引和信息”。后者通常称为键和值，合在一起叫 KV 缓存。

**例子：** 同样面对一篇旅行介绍，一个问题关注交通，另一个关注饮食。可查阅的文档相同，查询不同，所以算出的关注比例也不同。

### 前缀树

**大白话：** 把相同开头画成一段共同树干，不同后续内容画成不同树枝。

**例子：** 两个请求是“同一篇文档＋问题甲”和“同一篇文档＋问题乙”。文档是一段公共树干，两个问题是私有分支。这里要求实际词元序列的开头相同，仅仅意思相似不能直接共用。

### 查询分组与硬件对齐

**大白话：** 把适合一起计算的查询排成一组，让矩阵计算单元一次做更多有效工作。昇腾的这类矩阵单元常叫 Cube。

**例子：** 假设硬件适合一次处理 16 行，只有 3 行时可能也要按一块执行，剩余位置用填充占着。把多个请求的查询安排到一起，有机会让块更满；分组太散或共享太少，又可能增加额外工作。

### 分段计算与统一比例

**大白话：** 长上下文可以拆成几段计算，但每段结果不能直接平均。最后必须按它们在完整上下文中的关注份额合并。

**例子：** 一段获得总关注份额 3，另一段只有 1，那么两段不能各占最终结果的一半。常说的归一化，就是把这些权重换成总和为 1 的比例。

### 分组计划复用

**大白话：** 输入开头通常不会在每个生成步骤都变化，没必要每步重新规划整棵树。可以保留公共计划，只更新各请求新增长的尾部。

**例子：** 生成一句十六单位的回答时，文档部分始终相同。反复为文档重新分组，可能比省下的计算还贵。

## 4. 用一个小场景走一遍

先看存储。四个请求都包含同一段 100 单位的开头，各有 10 单位不同的问题。

如果各存一份，需要保存 440 个位置；共用开头后，是公共的 100 加四份私有的 10，共 140 个位置。这是教学例子，只表示可复用的数据数量，不能直接换算成整模型显存下降比例。

执行时，把多个请求的查询与共同开头一起计算，再分别处理私有分支。每个请求最后都要合并公共与私有部分。

再看合并。对某一个请求，假设已经把注意力分数换成正权重，但尚未调整到总和为 1：

- 公共段有两个值 0 和 6，权重分别为 2 和 1。这段总权重为 3，段内结果为 2。
- 私有段有一个值 10，权重为 1。这段总权重为 1，段内结果为 10。

如果把两个段内结果直接平均，会得到 6，这是错的。完整结果要按总权重 3 比 1 合并，得到 4。你也可以直接对三个值一起算，得到相同的 4。

实际内核还保存用于稳定计算的最大分数等信息，合并时统一不同段的数值尺度，避免某些分数很大时出错。它改变分块与分组方式，保留完整上下文注意力的数学含义。

项目比较了逐请求、固定分组、局部贪心分组和动态规划。贪心主要看眼前分支怎么拆；动态规划把后续分支的代价一起考虑，在给定成本模型和候选划分中选方案。这个最优是对模型而言，真实耗时仍要测。

实测中，128 个请求各有 8,192 长度、其中 8,128 是公共开头时，动态分组的注意力约 2.523 毫秒，厂商较快路径约 2.839 毫秒，加速约 1.126 倍。但同规模完全不共享时，树形路径反而慢约 13.73 倍。

规划成本也不能漏。在另一个连续生成实验中，复用动态计划把“规划加注意力”从每步约 3.896 毫秒降到 0.606 毫秒；更简单的固定分组复用计划为 0.536 毫秒，还更快。

接入真实 Qwen3-4B 后，共享文档问答的完整生成时间从约 1,192.0 毫秒降到 1,173.8 毫秒，约减少 1.5%。其他模型计算仍占时间，因此不能把小范围的 6.43 倍规划加速当成整模型加速。

## 5. 常见误解

- **“共用开头，就能共用整个注意力答案。”** 查询不同，对同一内容的关注不同；共享的是内容存储和读取机会，每个请求仍有自己的结果。
- **“分段结果各自算对，直接平均就对。”** 每段总关注份额不同，必须统一归一化后合并。
- **“算法更复杂，或者数学相同，就一定更快且逐字一致。”** 复杂规划可能抵消收益；浮点舍入也可能让接近并列的候选词换顺序。数学含义一致与输出文字完全相同需要分别检查。

## 6. 上手步骤与检查清单

1. 先手画“四个请求共用一段文档”的树，再手算上面的分段合并，确认每个请求应恰好覆盖自己的全部上下文。
2. 按[使用说明](../README.md)先运行 `tests` 下的主机测试，再用 `scripts/check_npu.py` 对照独立完整注意力。启动前加载昇腾环境，确认目标卡健康、空闲。
3. 从有共享、无共享和不等长分支各选一个小例子，检查是否漏算、重复计算或错误合并。
4. 比较逐请求、固定、贪心和动态方案，同时记录初次分组、数据排列转换和后续复用耗时。注意保留厂商算子对照。
5. 再用 `scripts/check_qwen.py` 检查模型接入，最后运行完整生成比较。正确性检查尽量让不同路径使用相同历史和相同输入中间值，避免生成分歧后拿不同问题互相比较。

## 7. 一句话总结

共享前缀注意力的收益取决于共享长度、请求数量和规划成本，正确分段合并与真实端到端对照缺一不可。

## 面试问答

### 问题一 你的工作与普通前缀缓存有什么不同

**中文回答：** 普通缓存主要复用已经算好的前缀中间数据。本项目进一步研究生成阶段怎样把查询分组，共享读取这些内容，并用昇腾矩阵单元执行分段注意力；还包含树形计划和生成尾部的更新。

**Question:** How does this differ from ordinary prefix caching?

**Answer:** Prefix caching reuses previously computed prefix states. This project additionally groups decode queries to reuse reads of shared KV data, executes segmented attention on Ascend matrix units, and manages tree schedules and growing decode tails.

### 问题二 分段以后怎样保持完整注意力

**中文回答：** 每个请求的上下文必须恰好覆盖一次。每段除了结果，还保存归一化所需的信息，合并时还原各段在全局中的权重。不能直接平均局部输出，尤其不能忽略长短段的权重差异。

**Question:** How do you preserve full attention across segments?

**Answer:** Each request's context must be partitioned exactly once. Segments retain both partial outputs and normalization information. The merge uses their global weights rather than averaging local outputs, preserving full-context attention across unequal segments.

### 问题三 动态规划一定胜过固定或贪心分组吗

**中文回答：** 不一定。它优化的是给定的分析成本模型，规划本身也花时间。81 种树形上，动态核相对固定和贪心的几何平均加速只有约 1.008 倍和 1.005 倍，没有显示普遍优势。

**Question:** Does dynamic programming always outperform fixed or greedy grouping?

**Answer:** No. It optimizes a particular analytical cost model and adds planning overhead. Across 81 trees, resident kernel speedups over fixed and greedy grouping are only about 1.008 and 1.005 times geometrically averaged. There is no broad advantage over simpler grouping.

### 问题四 哪些情况最可能受益

**中文回答：** 许多请求共用较长开头、计划能多次复用时更有机会。128 请求的长共享案例超过厂商算子，但无共享的对应案例很慢。真实模型共享文档问答的完整生成只改善约 1.5%，说明其他计算限制了总体收益。

**Question:** Which workloads are most likely to benefit?

**Answer:** Many queries sharing a long prefix, with reusable plans, offer the best opportunity. The 128-request shared case beats the vendor operator, while its unshared counterpart is much slower. Complete Qwen3-4B document-QA generation improves by only about 1.5% because other model work dominates.

### 问题五 如果生成文字不同 是否说明实现错误

**中文回答：** 需要检查，不能直接下结论。多分支实测的词元一致率是 89.84%。追查发现候选分数接近或并列，低精度舍入会改变选择；用相同历史和相同查询、键、值对照独立高精度注意力，相关逐层检查通过。但我不会宣称所有生成逐字一致。

**Question:** Does a different generated continuation prove the kernel is wrong?

**Answer:** It requires investigation. Multi-branch token agreement is 89.84%; near-tied BF16 logits resolve differently across numerical paths. Layer checks using identical histories and Q/K/V pass against independent FP32 attention. This supports attention correctness but does not establish identical continuations for every workload.
